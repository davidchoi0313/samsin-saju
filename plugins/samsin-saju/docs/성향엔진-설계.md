# 성향 엔진 설계서 (mbti_engine) — 만세력과 대칭되는 결정론 성향 산출 (승인 대기 초안)

> 문서 성격: **승인 대기 초안** — 담당자님 승인 전까지 실제 코드(`mbti_engine.py`)·SKILL 배선·계약(`reference/mbti-layer.md`)은 건드리지 않는다. 본 문서는 **설계·I/O 계약·스키마까지만**이며, 실코드 구현은 승인 후 개발 팀장 소관이다.
> 대상 플러그인: `plugins/samsin-saju/` (삼신이 사주풀이 · saju-reading 단일 창구)
> 짝 문서: `docs/사주-MBTI-완전융합-기획안.md`(본 설계를 엔진×엔진으로 반영한 상위 기획안). 본 문서는 그 부록 B(엔진 설계서)에 해당한다.
> 근거 기반: `scripts/saju_engine.py`(만세력 엔진 실파일 Read 완료 — I/O 계약·결정론 방식 확인) · `scripts/mbti_util.py`(현행 자기보고 파싱 유틸) · `reference/mbti-layer.md`(분리 계약·5대 가드·스키마) · `reference/input-form.html`(현행 입력 폼).
> 담당자님 통찰(설계 출발점): **"만세력 엔진처럼 성향(MBTI)도 엔진으로 돌려야 한다."** 현행은 사주=결정론 엔진 vs 성향=LLM 자기보고 레이어로 **비대칭**이라, 성향 쪽에서 'LLM 환각'이 되살아난다. 이 비대칭을 없애기 위해 만세력과 대칭되는 **결정론 성향 엔진**을 세우고, 융합을 "엔진×엔진"으로 재정의한다.
> 전 항목 `[변동 가능]` 원칙: 통과율·토큰 단가·문항 문구는 모델·시점 의존 예시값.

## 0. 한 줄 요지 (30초)

**성향 엔진(mbti_engine)은 만세력 엔진(saju_engine)과 나란히 놓이는 두 번째 결정론 모듈이다.** 만세력이 `생년월일시·성별·음양력 → (규칙) → 사주 카드`를 LLM 개입 0으로 고정하듯, 성향 엔진은 `유형/문항 입력 → (규칙) → 성향 카드`를 LLM 개입 0으로 고정한다. 이로써 융합은 **"LLM 자기보고 레이어 × 결정론 엔진"의 비대칭**에서 **"결정론 엔진 × 결정론 엔진"의 대칭**으로 승격된다.

단, **결정론이 두 엔진에서 뜻하는 바가 다르다.** 만세력의 결정론은 확립된 역법 계산이라 '정확'이지만(§4), 성향 엔진의 결정론은 **재현성(같은 입력→같은 카드)일 뿐 과학적 타당성 보증이 아니다** — 융(C.G. Jung) 심리유형론 기반의 **이론적 매핑**이기 때문이다. 이 구분(§4)이 본 설계의 안전 척추다.

## 1. 왜 엔진인가 — 비대칭이 만든 구멍 (문제 정의)

### 1.1 현행 비대칭 진단 (실파일 Read 근거)

| 축 | 사주 쪽 | 성향 쪽(현행) | 비대칭이 낳는 것 |
|---|---|---|---|
| 산출 주체 | **결정론 엔진** `saju_engine.py` (`build_card()`) | LLM 해석 레이어 + 얕은 파싱 유틸 `mbti_util.py`(`build_mbti_profile()`) | 성향 값의 '해석'이 LLM 손에 남음 |
| 산출물 | 구조화 카드(JSON) — 오행·십성·용신·대운… | `mbti_profile` 4글자 코드 + 4축 분해까지만 | 성향은 '카드'가 아니라 '코드 조각'에 그침 |
| 재현성 | 같은 입력 → 항상 같은 카드(엔진 원칙 명문) | 코드 파싱은 재현적이나, **그 코드를 성향 서술로 푸는 일은 LLM 매번 다름** | 성향 서술에서 'LLM 환각' 재발 |
| 융합 시 지위 | 사주 사실(팩트) | 자기보고 참고값(팩트 아님) | 엔진×레이어 비대칭 |

핵심 구멍: 현행 `mbti_util.py`는 `INTJ`를 받아 `axes:{EI:I,SN:N,TF:T,JP:J}`까지만 만든다(실파일 확인). "그래서 이 사람의 의사결정 결·소통 결·인지기능 스택이 무엇인가"는 **LLM이 매번 즉석에서 짐작**한다. 이 짐작 지점이 담당자님이 지적한 "성향 쪽 LLM 환각"의 정확한 위치다.

### 1.2 처방 — 짐작을 규칙으로 내리기

성향 엔진은 이 짐작 구간을 **결정론 규칙 산출**로 끌어내린다. `ai-product-manager` §3.2의 첫 질문 "이 문제, AI 없이 결정적 로직으로 풀 수 없나"에 대한 답이 바로 이것이다 — **유형→인지기능 스택→파생 성향 태그는 규칙표로 100% 결정 가능**하다(융 유형론의 확립된 스택 규약). LLM이 할 몫이 아니다. LLM은 이 카드를 **삼신이 목소리로 서술**하는 일(확률적·창의 영역)만 맡는다.

> **결정적/확률적 분리(ai-product-manager §3.1 정합):** 성향 카드 **산출**은 결정적(100% 강제 가능) → 엔진으로. 성향 카드를 **서술**하는 문장은 확률적 → 2층 LLM + 평가셋 통과율로.

## 2. 성향 엔진의 결정론 정의 (과제 1)

### 2.1 결정론 계약 — 만세력과 나란히

| 계약 항목 | 만세력 엔진(saju_engine) | 성향 엔진(mbti_engine) |
|---|---|---|
| 입력 → 출력 | `입력 dict → 사주 카드 dict` | `입력 dict → 성향 카드 dict` |
| 결정론 보증 | 같은 입력 → 항상 같은 카드 (`build_card()` 원칙 명문) | **같은 입력 → 항상 같은 카드** (동일 원칙 이식) |
| LLM 개입 | 0 (엔진은 순수 계산) | **0** (엔진은 순수 규칙 룩업) |
| 산출원 | `lunar_python`(역법) + `shinsal_rules`/`jijanggan`(보강) | **내장 규칙표**(유형→기능스택·태그) + 문항 채점 산식(외부 라이브러리 불요) |
| 면책 문구 | 카드에 안 넣음(2층 강제) | **카드에 안 넣음**(2층 강제 — 동일) |
| 무접점 원칙 | — | `saju_engine.py`를 import하지 않음(사주 로직과 물리 분리 — `mbti_util.py` 무접점 원칙 계승) |

### 2.2 입력 소스 2경로 — 같은 카드로 수렴

성향 엔진은 서로 다른 두 입력을 받되, **둘 다 같은 성향 카드 스키마로 수렴**시킨다.

**경로 (a) — 유형 직접 입력 (4글자/16유형)**
```
입력: {"mode":"type", "type":"INTJ"}
  │  ① 파싱·검증 (mbti_util.parse_mbti_type 계승 — 16유형 유효성)
  │  ② 4축 분해 {EI:I, SN:N, TF:T, JP:J}
  │  ③ 인지기능 스택 결정론 도출 (§3.2 규칙표 룩업 — 주기능·부기능·3차·열등)
  │  ④ 파생 성향 태그 도출 (§3.3 규칙표 룩업 — 의사결정·소통·에너지·실행 결)
  │  ⑤ 선호 명확도 = null (직접 입력은 강도 정보 없음), 신뢰도 = "self_declared"
  ▼
성향 카드 (§3.1 스키마)
```

**경로 (b) — 약식 문항 입력 (4축 × N문항)**
```
입력: {"mode":"quiz", "answers":{EI:[...], SN:[...], TF:[...], JP:[...]}}
  │  ① 축별 점수 집계 (문항 응답 → 각 축 -N..+N 결정론 합산)
  │  ② 축별 선호 방향 + 선호 명확도(clarity) 산출 (§3.4 산식)
  │  ③ 4글자 유형 확정 (각 축 부호 → E/I·S/N·T/F·J/P)
  │  ④ ③부터는 경로(a)의 ②~④와 동일 규칙 (인지기능 스택·파생 태그)
  │  ⑤ 선호 명확도 = 산출값, 신뢰도 = "quiz_derived"(문항수·clarity 기반)
  ▼
성향 카드 (§3.1 스키마 — 경로(a)와 동일 구조)
```

**수렴 지점(핵심):** 두 경로는 **"4글자 유형이 확정된 시점"에서 완전히 합류**한다. 그 뒤 인지기능 스택·파생 태그 도출 규칙은 두 경로가 **한 글자도 다르지 않다.** 차이는 딱 두 필드 — `preference_clarity`(a는 null, b는 산출값)와 `confidence`(a는 self_declared, b는 quiz_derived)뿐이다. 이것이 "두 경로 → 같은 카드" 보증이다.

```
   경로(a) 유형 직접 ─┐
                      ├─→ [4글자 유형 확정] ─→ [기능스택 룩업] ─→ [파생태그 룩업] ─→ 성향 카드
   경로(b) 약식 문항 ─┘         ▲                (두 경로 공통 규칙 — 분기 없음)
                        b는 여기서 clarity·confidence만 추가 채움
```

### 2.3 결정론 보증 규칙 (LLM 개입 0)

- **모든 도출은 룩업 또는 산술.** 인지기능 스택(§3.2)·파생 태그(§3.3)는 **16행 규칙표 룩업**, 문항 점수(§3.4)는 **정수 합산·부호 판정**뿐이다. 자유 생성·추론이 없다.
- **같은 입력 → 같은 카드.** `INTJ`는 몇 번을 넣어도 같은 스택·같은 태그를 낸다. 문항 응답도 같은 답 배열이면 같은 점수·같은 clarity를 낸다.
- **엔진은 서술하지 않는다.** 카드는 태그·값·라벨만 담는다. "너는 이런 사람"이라는 **문장은 엔진이 만들지 않는다**(2층 LLM 몫). 만세력이 "너는 을목이라 여리다"를 안 쓰고 `dayMaster:{gan:乙, element:木}`만 내는 것과 정확히 대칭.

## 3. 성향 카드 스키마 (출력 계약 · 과제 2)

### 3.1 카드 구조 — 만세력 카드와 나란히

성향 카드는 만세력 카드(`brand`·`meta`·`input`·`pillars`…)와 **나란히 놓이는 두 번째 카드 JSON**이다. 만세력 카드에 **병합하지 않는다**(무접점 — mbti-layer §1 분리 계승). 융합은 2층에서 두 카드를 나란히 참조하는 방식(§5)이다.

```json
{
  "mbti_card": {
    "brand": "samsin",
    "engine": "mbti_engine",
    "meta": {
      "inputMode": "quiz",
      "provided": true,
      "note": "self-reported / theory-based mapping. NOT a saju fact. NOT a clinical test. tone/advice personalization only."
    },
    "type": "INTJ",
    "axes": { "EI": "I", "SN": "N", "TF": "T", "JP": "J" },
    "preferenceClarity": { "EI": 0.72, "SN": 0.90, "TF": 0.55, "JP": 0.68 },
    "cognitiveStack": {
      "dominant":  { "function": "Ni", "label": "내향 직관" },
      "auxiliary": { "function": "Te", "label": "외향 사고" },
      "tertiary":  { "function": "Fi", "label": "내향 감정" },
      "inferior":  { "function": "Se", "label": "외향 감각" }
    },
    "traitTags": {
      "decision": "따져 납득하는 결",
      "communication": "혼자 정리해 꺼내는 결",
      "energy": "안으로 채우는 결",
      "execution": "계획해 두는 결"
    },
    "dominantAxes": ["SN", "EI"],
    "confidence": { "level": "quiz_derived", "score": 0.71 }
  }
}
```

### 3.2 필드별 결정론 계산 규칙 (표)

| 필드 | 뜻 | 결정론 계산 규칙 | 만세력 대응(대칭) |
|---|---|---|---|
| `engine` | 산출 엔진 표식 | 상수 `"mbti_engine"` | `brand:"samsin"` |
| `meta.inputMode` | 입력 경로 | `"type"`(직접) / `"quiz"`(문항) 중 입력이 정함 | `meta.calendar` |
| `meta.provided` | 성향 제공 여부 | 유효 입력이면 `true`, 무효/미입력이면 `false`(강등) | — (사주는 항상 provided) |
| `meta.note` | 성격 라벨 | 상수 — **"자기보고/이론 기반 매핑·사주 사실 아님·임상검사 아님·톤 개인화 전용"** 4중 못박음 | (카드엔 면책 없음 — 대칭) |
| `type` | 4글자 유형 | (a)직접값 / (b)4축 부호 판정 결과 | `dayMaster.gan`(핵심 식별자) |
| `axes` | 4축 분해 | `type` 4글자를 `{EI,SN,TF,JP}`로 자리별 매핑 | `pillars`(구성 요소 분해) |
| `preferenceClarity` | 축별 선호 명확도 0~1 | (a) 전부 `null` / (b) §3.4 산식 (\|축점수\|/최대점수) | `fiveElements.strength`(강약 정도) |
| `cognitiveStack` | 인지기능 스택 4단(주·부·3차·열등) | **16유형→스택 규칙표 룩업**(§3.2-A 규약) — LLM 개입 0 | `fiveElements`/`tenGods`(구조 산출) |
| `traitTags` | 파생 성향 태그 4결 | §3.3 규칙표 룩업 — 축 조합→의사결정·소통·에너지·실행 결 | `yongshin.candidates`(파생 처방 후보) |
| `dominantAxes` | 가장 도드라지는 1~2축 | (a) 규칙표 우선순위 / (b) clarity 상위 2축 | `fiveElements.dominant`(과다 오행) |
| `confidence` | 신뢰도 | (a) `self_declared`(고정) / (b) 문항수·평균 clarity로 산출 | `meta.hourKnown`(정보 충실도 신호) |

**§3.2-A 인지기능 스택 룩업 규약 (결정론 핵심):**
융 유형론의 확립된 스택 규칙을 16행 테이블로 못 박는다. 규칙(재현 가능한 표준 매핑):
1. 4번째 글자(J/P)가 **주기능이 판단형(T/F)이냐 인식형(S/N)이냐**를 정한다 — 외향(E)이면 J=판단기능 외향, 내향(I)이면 J=인식기능 외향(축 뒤집힘 규약).
2. 주기능의 방향(E/I)은 1번째 글자를 따르고, 부기능은 반대 방향·반대 범주.
3. 3차 = 부기능의 반대극, 열등 = 주기능의 반대극(방향도 반대).

예: `INTJ` → 주 Ni · 부 Te · 3차 Fi · 열등 Se (위 스키마 예시와 일치). 이 규칙은 **16유형 전부에 대해 유일한 스택을 결정**하므로 룩업 테이블 1장으로 표현된다. ⚠ 이 매핑은 **재현 가능한 이론 규약**이지 과학적 타당성 보증이 아니다(§4).

### 3.3 파생 성향 태그 규칙 (traitTags)

각 태그는 **정해진 축을 룩업**한다(축 조합이 아니라 단일 축 우선 — 결정론·투명성 위해).

| 태그 | 결정 축 | 규칙(값 → 태그) |
|---|---|---|
| `decision`(의사결정 결) | TF | T→"따져 납득하는 결" / F→"마음·관계를 먼저 보는 결" |
| `communication`(소통 결) | EI | E→"사람들과 나누며 꺼내는 결" / I→"혼자 정리해 꺼내는 결" |
| `energy`(에너지 결) | EI | E→"사람 사이서 채우는 결" / I→"안으로 채우는 결" |
| `execution`(실행 결) | JP | J→"계획해 두는 결" / P→"마음 가는 대로 가는 결" |

라벨 문구는 **mbti-layer §1.3 번역 사전('성향결' 언어)과 정합하는 고정 문자열**이다. 엔진이 이 확정 문자열을 카드에 담고, 2층 LLM은 이 문자열을 문맥에 녹여 서술만 한다(새 표현 창작이 아니라 룩업 문자열 활용). **유형코드·축코드는 태그 문자열에 들어가지 않는다**(가드 5 정합 — 카드 내부엔 `axes` 코드가 있으나 `traitTags`는 이미 '성향결'로 번역돼 있어 2층이 그대로 써도 노출 0).

### 3.4 문항 채점·선호 명확도 산식 (경로 b)

- **축 점수:** 각 축 문항에 방향값(±1)을 부여해 합산 → 축점수 ∈ [−N, +N] (N=축당 문항수).
- **선호 방향:** 부호. 양수면 앞글자(E/S/T/J), 음수면 뒷글자(I/N/F/P). **0(동점)이면 규칙상 뒷글자로 고정**(임의 아님·재현 보장).
- **선호 명확도(clarity):** `|축점수| / N` ∈ [0,1]. 1에 가까울수록 그 축 선호가 뚜렷. 0.5 미만은 '약한 선호'.
- **신뢰도(confidence.score):** 4축 clarity 평균. `level`은 문항수 충분+평균 clarity 기준으로 `quiz_derived`(정상) 또는 저문항/저clarity 시 하향 신호.

> **왜 clarity를 카드에 담나:** 만세력이 `fiveElements.strength`(신강/신약/중화)로 '정도'를 담듯, 성향도 '선호가 얼마나 뚜렷한지'를 담아야 2층이 과단정을 피한다. clarity 0.55(TF)면 2층은 "따지는 결이 살짝 있는 편" 정도로만 눅여 서술(과신 차단 — ai-product-manager §3.3 신뢰 보정 정합).

## 4. 엔진 지위 상승에 따른 안전·정직 재조정 (과제 4)

### 4.1 결정론 = 재현성 ≠ 과학적 타당성 (명문화 · 안전 척추)

> **두 엔진의 결정론은 층위가 다르다.** 이 구분을 흐리면 성향 엔진이 '성향을 과학적으로 판정하는 검사'로 오인될 위험이 커진다 — 그것이 승격이 만드는 가장 큰 새 리스크다.

| 구분 | 만세력 엔진 | 성향 엔진 |
|---|---|---|
| 결정론의 뿌리 | **확립된 역법 계산**(절기·간지·음양력 변환) | **융 심리유형론 기반 이론 매핑** |
| "같은 입력→같은 출력"의 의미 | 재현성 **그리고** 역법상 정확 | **재현성뿐** |
| 과학적 타당성 | (역법 자체는 확정 계산) | **보증하지 않음** — 이론 기반·자기보고 기반 |
| 정직 라벨(불변) | "오락·참고" | **"오락·참고 + 자기보고 + 이론 기반 매핑 + 임상검사 아님"** |

**핵심 명제(문서 전체에 관통):** *"성향 엔진은 재현 가능하다. 재현 가능하다는 것이 '맞다'는 뜻은 아니다. 엔진은 입력을 이론 규약대로 항상 같게 변환할 뿐, 그 규약이 사람을 과학적으로 규정한다고 주장하지 않는다."* — psychologist §3.6 정합: **명명된 프레임(융 유형론) + 이론의 한계 1줄 + "임상/과학 검사 아님" 고지**를 카드 `meta.note`와 2층 면책에 못 박는다.

### 4.2 낙인·단정 차단 (엔진 승격 후에도 불변)

- **유형 낙인 0:** 엔진이 태그를 산출해도 "이 유형이라 못한다"류 우열 서술 금지(psychologist §5·mbti-layer §3.2 계승). 태그 라벨 자체가 '결의 차이' 문구로만 설계됨(§3.3).
- **인지기능 스택은 '결의 지도'지 '능력 판정'이 아님:** `inferior`(열등기능)를 "약점·못하는 것"으로 서술 금지. "덜 익숙한 결"까지만. 카드는 값만 주고, 2층이 낙인 없이 서술하도록 §5 융합 규칙이 강제.
- **단정 금지 유지:** "너는 반드시 이렇다" 금지 → "이런 결이 뚜렷한 편"(clarity 반영). 재현성이 단정 면허가 아님을 clarity 필드가 구조적으로 눅인다.

### 4.3 개인정보 정책 갱신 (엔진화가 바꾸는 것) ⚑

엔진화는 성향을 **구조화된 프로파일(스택·태그·clarity)**로 만든다 — 현행 `mbti_profile`(4글자+4축)보다 **정보 밀도가 높아진다.** 개인정보 민감도가 오르므로 정책을 갱신한다.

| 항목 | 현행(mbti_profile) | 엔진화(mbti_card) 후 |
|---|---|---|
| 저장 데이터 | 4글자 코드 + 4축 | **+ 문항 원응답(경로 b)·스택·태그·clarity** |
| 민감도 | 낮음(코드 조각) | **중간 — 성향 프로파일 + 생년월일 결합 시 상승** |
| 기본 정책 | 세션 내 값만(폼 localStorage 미사용) | **세션 비영속 기본 유지.** 문항 원응답은 카드 산출 후 **즉시 폐기 권장**(카드만 세션 보유) |
| 저장·프로파일링 | — | 저장·재사용·프로파일링 시 **개인정보 처리방침·동의 흐름 선행** ⚑ 법무 검토 |
| 약식 문항 응답 | (현행 없음) | 문항 응답 저장은 **동일 게이트** ⚑ (심리 문항이라 민감) |

⚑ **법무 검토 항목:** (1) 문항 원응답·성향 카드·생년월일 결합 저장/프로파일링 — 개인정보 처리방침·동의. (2) 약식 문항의 "성격검사 아님·오락 참고" 고지 문구 법적 적부. (3) 문항 원응답 즉시 폐기 정책의 문서화. **법령 근거·최종 문구는 법무 팀장이 확정**하며 본 설계는 자리만 표식한다.

### 4.4 기존 안전 바닥 유지 확인 (엔진 승격 후 대조)

| 안전 바닥(현행) | 엔진 승격 후 | 유지 방식 |
|---|---|---|
| 단정 금지 | **유지** | clarity 필드가 과단정을 구조적으로 눅임(§4.2) + 2층 단정 회피 규칙 |
| 면책 2단 | **유지** | 카드에 면책 안 넣음(2층 강제) + §5 성향 단서(이론 기반·임상검사 아님 추가) |
| 낙인 차단 | **유지** | 태그 라벨이 '결의 차이' 고정 문구(§3.3) + 10 신살 특례 불변 |
| 사주↔성향 상호 도출 금지 | **유지(핵심)** | 두 카드 물리 분리 + §5 융합에서 상호 도출 앵커 금지(가드 1·2 계승) |

## 5. 엔진×엔진 융합 로직 재정의 (과제 3)

### 5.1 승격 요지 — 레이어×엔진 → 엔진×엔진

현행 융합(기획안 §2)은 "**사주 카드 필드 × 성향 자기보고 4축**"이었다. 성향이 엔진 산출 카드로 승격되면서 융합은 "**사주 카드 필드 × 성향 카드 필드**"의 **대칭 결합**이 된다. 서술 문법은 그대로(사주=무엇을, 성향=어떻게·무엇부터)이되, 성향 쪽 재료가 'LLM 짐작'에서 '엔진 산출 태그·스택·clarity'로 바뀌어 **환각 여지가 사라진다.**

| 융합 축 | 현행(레이어) | 엔진×엔진(승격) |
|---|---|---|
| 사주 재료 | 엔진 카드 필드 | 엔진 카드 필드(불변) |
| 성향 재료 | LLM이 4글자로 즉석 짐작한 성향 서술 | **성향 카드 필드**(스택·traitTags·clarity — 엔진 산출) |
| 결합 대상 | 사주 필드 × 성향 축(코드) | **사주 필드 × 성향 필드**(둘 다 카드값) |
| 환각 여지 | 성향 서술에 남음 | **성향 서술도 카드 룩업 문자열 기반 → 여지 제거** |

### 5.2 사주 카드 필드 × 성향 카드 필드 대칭 매핑

| 사주 카드 필드(무엇을) | 성향 카드 필드(어떻게·무엇부터) | 융합 결과(한 문장 예) |
|---|---|---|
| `yongshin`(용신=약이 되는 기운) | `traitTags.decision` + `preferenceClarity` | "네게 약이 되는 물 기운을, 따져 납득하는 결이 뚜렷하니 '왜 필요한지'부터 짚고 실천해 보렴." |
| `tenGods`(십성=재주·책임 결) | `traitTags.communication`/`energy` | "표현하는 재주가 좋은데, 혼자 정리해 꺼내는 결이니 글로 먼저 꺼내 보렴." |
| `fiveElements`(오행 과다·불균형) | `traitTags.execution` | "치우친 기운은, 계획해 두는 결이면 순서를 정해 다독이면 된단다." |
| `daewoon`/`sewoon`(흐름 변화 시기) | `cognitiveStack.dominant`(주기능 결) | "흐름이 바뀌는 무렵엔, 큰 그림부터 잡히는 결이니 방향 한 줄을 먼저 품고 준비하렴." |

**성향 카드 필드가 새로 여는 표현력:** 현행은 4축 코드만 있어 "N결/T결" 수준이었으나, 엔진 승격 후 `cognitiveStack`·`clarity`가 생겨 **"주기능이 뚜렷한 결"(clarity 높음) vs "덜 익숙한 결"(inferior)**까지 결정론으로 짚을 수 있다. 단 이 표현은 **낙인 없이**(§4.2)만.

### 5.3 충돌 우선순위 (승격 후 재확인 — 안전>사주엔진 팩트>성향엔진 팩트)

| 우선순위 | 이기는 것 | 승격 후 변화 |
|---|---|---|
| 1순위 | 안전 바닥(면책·단정 금지·낙인 금지·중대결정 전문가 권유) | **불변** — 두 엔진 위 |
| 2순위 | **사주 엔진 팩트**(사주 카드) | 사주 사실의 유일 근거. 성향 카드가 덮어쓰기·보정 불가 |
| 3순위 | **성향 엔진 팩트**(성향 카드) | **레이어에서 '엔진 팩트'로 승격.** 단 '성향 팩트'는 재현성 팩트지 사주 팩트와 동급 아님(§5.4) |
| 미제공 시 | 사주 단독 | 성향 카드 `provided:false` → 3순위 통째 생략(사주 단독 폴백) |

**성향이 엔진 팩트로 오른 뒤에도 사주와 동급이 아닌 이유:** 사주 카드는 '사주 사실'(이 플러그인의 사실 정의), 성향 카드는 '자기보고를 이론 규약으로 재현한 값'이다. 그래서 2순위(사주) > 3순위(성향) 순서는 유지된다. **성향 카드가 사주 필드값을 바꾸는 경로는 여전히 존재하지 않는다.**

### 5.4 처방 근거 앵커(└ 근거)에 성향 카드 인용 경계 (신규 규정 · 과제 3 핵심)

성향이 '엔진 산출 팩트'로 승격됨에 따라, 처방의 `└ 근거` 앵커에 성향 카드 필드를 인용할 수 있는지를 **새로 규정**한다.

| 앵커 대상 | 인용 가능? | 규칙 |
|---|---|---|
| **사주 처방의 `└ 근거`** (오행·십성·용신·신살에서 나온 처방) | **성향 카드 인용 금지(불변)** | 사주 처방의 근거는 **오직 사주 카드 필드**. 성향 카드는 앵커 못 됨(가드 3 계승) |
| **전달·실천 방식의 근거** (처방을 '어떻게·무엇부터' 전하는 방식) | **성향 카드 인용 허용(신규)** | 성향이 엔진 팩트가 됐으므로, "이 실천을 계획 결로 권한 근거 = 성향 카드 `traitTags.execution`"는 인용 가능. 단 **사주 사실의 근거가 아니라 '전달 방식의 근거'로만** |
| **상호 도출** (사주↔성향) | **전면 금지(불변)** | "성향 카드가 이러니 사주에 관성이"·"사주가 이러니 유형이 INTJ" 어느 방향도 금지(가드 1·2). 두 카드는 **각자 자기 근거만** |

**경계 한 줄 규정:** *"성향 카드는 '왜 이 처방인가'(사주 근거)의 앵커가 될 수 없고, '이 처방을 왜 이렇게 전하나'(전달 방식)의 앵커는 될 수 있다."* — 사주 사실과 성향은 여전히 상호 도출 금지, 각자 자기 영역의 근거로만 인용된다. 이것이 엔진 승격이 앵커 규칙에 만든 유일한 변화다.

> 근거:
> - 내용: 엔진×엔진 융합 = 사주 카드 필드 × 성향 카드 필드 대칭 결합. 충돌 우선순위 안전>사주엔진 팩트>성향엔진 팩트 유지. 성향 카드는 사주 처방 근거 앵커 불가(불변), 전달 방식 근거 앵커는 신규 허용, 사주↔성향 상호 도출 전면 금지(불변).

```python
    """입력 dict → 성향 카드 dict.  같은 입력 → 항상 같은 카드(LLM 개입 0).
    inp["mode"] == "type" : inp["type"](4글자) 기반 경로(a)
    inp["mode"] == "quiz" : inp["answers"](축별 응답) 기반 경로(b)
    무효/미입력 → provided:false 카드(강등 — 예외 없음, mbti_util 계승)."""
```
- CLI 계약도 saju_engine와 대칭(`--mode type --type INTJ` / `--stdin` JSON) — 개발 시 확정.

### 6.3 I/O 구체 예시 1개 (과제 5 필수 — 경로 b)

**입력 dict (약식 문항 · 축당 3문항 예):**
```json
{
  "mode": "quiz",
  "answers": {
    "EI": [-1, -1, +1],
    "SN": [+1, +1, +1],
    "TF": [+1, -1, +1],
    "JP": [+1, +1, -1]
  }
}
```
*(값 규약: EI에서 +1=E쪽·−1=I쪽, SN에서 +1=S·−1=N, TF에서 +1=T·−1=F, JP에서 +1=J·−1=P.)*

**출력 카드 dict (결정론 산출 — 위 입력이면 항상 이 카드):**
```json
{
  "mbti_card": {
    "brand": "samsin",
    "engine": "mbti_engine",
    "meta": {
      "inputMode": "quiz",
      "provided": true,
      "note": "self-reported / theory-based mapping. NOT a saju fact. NOT a clinical test. tone/advice personalization only."
    },
    "type": "ISTJ",
    "axes": { "EI": "I", "SN": "S", "TF": "T", "JP": "J" },
    "preferenceClarity": { "EI": 0.33, "SN": 1.0, "TF": 0.33, "JP": 0.33 },
    "cognitiveStack": {
      "dominant":  { "function": "Si", "label": "내향 감각" },
      "auxiliary": { "function": "Te", "label": "외향 사고" },
      "tertiary":  { "function": "Fi", "label": "내향 감정" },
      "inferior":  { "function": "Ne", "label": "외향 직관" }
    },
    "traitTags": {
      "decision": "따져 납득하는 결",
      "communication": "혼자 정리해 꺼내는 결",
      "energy": "안으로 채우는 결",
      "execution": "계획해 두는 결"
    },
    "dominantAxes": ["SN"],
    "confidence": { "level": "quiz_derived", "score": 0.50 }
  }
}
```
*(산출 검산: EI 합 −1→I·clarity 1/3≈0.33 / SN 합 +3→S·clarity 3/3=1.0 / TF 합 +1→T·clarity 1/3≈0.33 / JP 합 +1→J·clarity 1/3≈0.33 ⇒ 유형 **ISTJ**. 예시로 SN만 뚜렷하고 나머지는 약한 선호임을 clarity가 드러냄. `ISTJ` 스택 = Si·Te·Fi·Ne(§3.2-A 규약 룩업). confidence.score = 4축 clarity 평균 (0.33+1.0+0.33+0.33)/4 ≈ 0.50.)*

### 6.4 SKILL 라우터·input-form.html 연동 지점

- **input-form.html:** 현행 폼은 16유형 pill + "몰라요"만 있다(실파일 확인). 엔진화 후 **"몰라요" 경로에 약식 문항(경로 b)을 선택 제공**한다 — "몰라요" 누르면 4축 각 1~3문항을 삼신이 보이스로 띄우고, 답하면 `mode:quiz` 입력으로 `build_mbti_card()` 호출. 유형 직접 선택은 `mode:type`. **입력 단계 유형코드 노출 허용은 불변**(폼 규약), 결과 출력은 '성향결'만(가드 5).
- **SKILL 라우터:** 사주 필수 입력 수집 → `saju_engine.build_card()` 호출과 **나란히** 성향 입력 있으면 `mbti_engine.build_mbti_card()` 호출 → **두 카드를 조력자(samsin-mansae/byeolnim)에게 함께 전달** → 조력자가 §5 융합 규칙으로 서술 → 삼신이 감쌈 + 면책 2단(+ 이론 기반·임상검사 아님 성향 단서).
- **폴백(성향 미입력):** `build_mbti_card()`가 `provided:false` 카드를 내면 2층은 성향 통째 생략, `saju_engine` 카드 단독 풀이(강등·오염 0 — 가드 4 계승). **성향 엔진은 미입력을 예외가 아니라 정상 폴백으로 처리**(mbti_util `_not_provided()` 정신 계승).

## 7. 실패 모드·대응 (설계 검증)

- **실패 1 — 재현성을 타당성으로 오독.** 대응: `meta.note` 4중 라벨 + §4.1 명제 + 2층 면책에 "이론 기반 매핑·임상검사 아님" 강제. **가장 중요한 실패 모드.**
- **실패 2 — 인지기능 스택이 '능력 판정'으로 낙인화(특히 열등기능).** 대응: §4.2 — inferior는 "덜 익숙한 결"까지만, 태그 라벨 고정 문구, 10 신살 특례 불변.
- **실패 3 — 성향 카드가 사주 처방 앵커로 새어듦.** 대응: §5.4 앵커 경계표 — 사주 처방 근거는 사주 카드만, 성향은 전달 방식 근거만. 상호 도출 전면 금지.
- **실패 4 — 문항 원응답 저장으로 개인정보 민감도 상승.** 대응: §4.3 — 문항 응답 카드 산출 후 즉시 폐기 권장, 저장 시 ⚑ 법무 게이트.
- **실패 5 — 엔진화로 성향 서술이 기계적·차가워짐.** 대응: 엔진은 태그/값만, **삼신이 다정한 서술은 2층 몫**(만세력도 카드는 무미건조·서술은 삼신이). 카드 승격이 페르소나를 바꾸지 않음.

## 부록. 거버넌스 위반 0 확인 문장

> **본 성향 엔진 설계는 삼신이 SKILL.md §0(엔진 산출만이 사주 근거) 위반 0을 유지한다.** 성향 엔진은 **사주 사실을 만들지 않는다** — 별도 성향 카드를 낼 뿐, `saju_engine.py`를 import하지 않고(무접점) 사주 카드 필드를 덮어쓰거나 보정하지 않는다. 성향 엔진의 결정론은 **재현성이지 과학적 타당성이 아니며**(§4.1), 카드 `meta.note`와 2층 면책이 이 라벨(자기보고·이론 기반·임상검사 아님)을 못 박는다. 사주↔성향 상호 도출은 두 카드 물리 분리와 §5.4 앵커 경계로 전면 금지되고, 유형코드·검사명은 사용자 출력에 노출되지 않으며(가드 5), 미제공 시 사주 단독 폴백으로 강등·오염이 없다. 채용참고(15)는 차별 리스크로 성향 결합 대상에서 계속 제외된다. 사용자 대면 화자는 여전히 삼신이 하나다. 실코드 구현은 승인 후 개발 팀장 소관이며 본 문서는 설계·I/O 계약·스키마까지만이다.
